8. The Terminal Approach — How & Why

1
Open the correct terminal.
Start → search Developer Command Prompt for VS 2022 → open it.
2
Move into the Hydra folder. 
cd /d C:\Users\%USERNAME%\Downloads\hydra
3
Force the build to use VS2022/v143. 
set VCPKG_KEEP_ENV_VARS=VSCMD_VER;VisualStudioVersion;VSINSTALLDIR;VCINSTALLDIR
set CMAKE_GENERATOR=Visual Studio 17 2022
set VCPKG_FORCE_SYSTEM_BINARIES=1
set VCPKG_VISUAL_STUDIO_PATH=C:\Program Files (x86)\Microsoft Visual Studio\2022\BuildTools
set VCPKG_PLATFORM_TOOLSET=v143
set CMAKE_GENERATOR_PLATFORM=x64

echo %CMAKE_GENERATOR%
where cl
4
Start Hydra in development mode. 
yarn dev
Why keep the terminal open?
  • Hydra's development process is running from that terminal.
  • You can see Electron, Vite, native-addon and runtime messages.
  • If something fails, the error is visible immediately.
  • You can stop everything cleanly with Ctrl + C.
Important: an open terminal is not a security feature by itself. We use it because it gives us visibility while we investigate the application. The actual security work comes from checking the source, dependencies, network activity, files/processes and scan results.

9. Install Hydra Dependencies

yarn install

Let it finish completely. The postinstall builds the native Hydra addon and prepares native Electron dependencies.

Do not follow old Python/libtorrent instructions.
For this native build, do not run pip install -r requirements.txt just to install the torrent component. That older route caused a Python 3.14/libtorrent compatibility error during the earlier setup.

Check Electron

if exist node_modules\electron\dist\electron.exe (echo Electron OK) else (echo Electron MISSING)

If Electron is missing for the v4.1.4 setup:

yarn add electron@40.9.3 --dev

  • Renderer development server starts
  • Hydra window opens normally

12. Security Check Workflow

This is the research phase before making a production installer. The goal is to understand what the program is doing rather than assuming that a successful build automatically means everything is safe.

01 · Source
Use the official repository. Check commits, dependencies and scripts.
02 · Build
Watch terminal output for unexpected downloads, scripts or failures.
03 · Network
Record domains and connections made while Hydra is running.
04 · Processes
Check child processes and anything launched in the background.
05 · Files
Look for unusual files created outside expected application folders.
06 · Scans
Use reputable antivirus/malware scanners and record exact results.
Research rule: a warning, detection or unknown connection is something to investigate—not automatic proof of malware. Record the exact file, process, domain, timestamp and scanner result before drawing conclusions.

Future checks to add to this guide

  • Windows Defender / Microsoft Security scan results
  • VirusTotal results for the exact built artifact
  • Windows process tree observations
  • Network connection observations
  • Installed dependency audit
  • Unexpected startup/background process findings
  • Hash values for released artifacts

What was confirmed today

AreaConfirmed evidence
BaselineCreated process, network and filesystem snapshots under security-research before any game download test.
Hydra endpointsThe current build uses the configured Hydra API and authentication endpoints. Electron HTTPS connections were observed during runtime; connection timing and owning PIDs were recorded in the baseline work.
Download source flowAdding a source sends its URL to Hydra's /download-sources API; the main process stores the returned source object locally. Profile sync is a separate API step.
Source fetching modelDownloadSource.url is the registry/source URL, while DownloadSourceDownload.uris contains actual download URIs. The source-sync code itself does not directly fetch the source URL.
URI selectionHydra recognizes specific host prefixes plus magnet: rather than treating every arbitrary HTTPS URI as a downloader.
Downloader executionHoster URIs are resolved by provider-specific code before the final download payload is created. Torrent downloads are handed to the native libtorrent path.
Hydra downloader branchThe internal Downloader.Hydra branch in DownloadManager throws NotCachedOnHydra instead of directly executing an arbitrary URI.
Final splitDownloadManager.startDownload() separates HTTP downloads from native libtorrent. HTTP uses JsHttpDownloader; torrent payloads go through TorrentService.call().
HTTP pathThe resolved URL, headers, filename and save path are passed into the JavaScript HTTP downloader, which invokes executeDownload().

14. Troubleshooting

A. spawn cargo ENOENT

Rust is not available to the current terminal.

where cargo
where rustc

Open a new VS2022 Developer Command Prompt.

B. CMake says Visual Studio 18

The environment is using VS2026.

set VCPKG_KEEP_ENV_VARS=VSCMD_VER;VisualStudioVersion;VSINSTALLDIR;VCINSTALLDIR
set CMAKE_GENERATOR=Visual Studio 17 2022
set VCPKG_FORCE_SYSTEM_BINARIES=1
set VCPKG_VISUAL_STUDIO_PATH=C:\Program Files (x86)\Microsoft Visual Studio\2022\BuildTools
set VCPKG_PLATFORM_TOOLSET=v143
set CMAKE_GENERATOR_PLATFORM=x64

C. __std_* unresolved linker errors

This indicates mixed MSVC toolsets. Check:

where cl

It should point to VS2022 Build Tools.

D. node-gyp rejects Visual Studio

Use VS2022 Build Tools and run the install from its Developer Command Prompt.

E. undefined.includes("staging")

Check the environment:

findstr /N /I "MAIN_VITE_API_URL MAIN_VITE_AUTH_URL" .env

Both values should be populated as shown in the .env section. Restart Hydra after changing .env.

F. Sign-in window / DevTools disconnect

In development mode Hydra can open DevTools for the separate authentication window. If the auth window disconnects or is blank, first verify MAIN_VITE_AUTH_URL=https://auth.hydralauncher.gg, then restart yarn dev.

G. "No downloads available"

This is separate from the compiler/build process. Hydra's catalogue and download sources are separate. Third-party download sources should be treated as independent trust decisions.

H. Vite dynamic-import warnings

Messages about dynamic imports not moving modules into another chunk can be bundling warnings rather than fatal failures.

Why This Guide Uses This Approach

  • Terminal first: visibility into errors and runtime behavior.
  • Official source: avoid random forks or prebuilt binaries during the research phase.
  • Build Tools instead of the full IDE: only the Windows C++ build components needed by the native build.
  • No obsolete Python/libtorrent route: use the project's current native build path.
  • One MSVC toolchain: avoids the VS2026/VS2022 mismatch that caused linker errors.
  • Environment variables checked: prevents development startup failures caused by missing values.
  • Security checks before packaging: investigate behavior before treating the final application as trusted.
